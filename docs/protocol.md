# USBCAN 协议摘要

本文记录实现所依赖的字节级协议约束。权威来源为
`can_service/usbcan_driver_gs`（C 参考驱动）与
`can_service/multi-can/crates/usbcan-async`（Rust 异步实现）。

设备：创芯科技 USBCAN/CANalyst-II，VID:PID `04d8:0053`，固件 CAN-Linux V3.51。
单 USB 接口（interface 0），双 CAN 通道。

## 端点

| 通道 | 命令 OUT | 数据 TX | 数据 RX |
| --- | --- | --- | --- |
| CAN1 (0) | `0x02` | `0x01` | `0x81` |
| CAN2 (1) | `0x04` | `0x03` | `0x83` |

命令 IN 端点 = 命令 OUT | `0x80`（如 `0x0A` 查询响应从 `0x82` 读取）。

## 命令包

固定 64 字节，发送到通道命令端点。

| 命令 | 值 | 说明 |
| --- | --- | --- |
| InitCAN | `0x01` | 初始化通道 |
| StartCAN | `0x02` | 启动通道 |
| ResetCAN | `0x03` | 复位通道 |
| Close | `0x07` | 关闭设备，必须发到两个通道命令端点 |
| GetReceiveNum | `0x0A` | 查询接收缓冲帧数 |
| ClearBuffer | `0x0B` | 清空接收缓冲 |
| SetReference | `0x0E` | 滤波参考 |
| Handshake | `0x13` | 挑战-应答握手 |

## InitCAN / StartCAN

有效长度 56 字节，发送时补零到 64：

| 偏移 | 内容 |
| --- | --- |
| `[0]` | 命令字 `0x01` / `0x02` |
| `[4..8]` | AccCode，小端 u32 |
| `[8..12]` | AccMask，小端 u32 |
| `[16]` | Filter 方式（0 全部 / 1 单滤波 / 2 双滤波） |
| `[24]` | Timing0 |
| `[28]` | Timing1 |
| `[32]` | Mode（0 正常 / 1 只听 / 2 自测） |
| `[36]` | `0x01` |
| `[40..56]` | `0x340` 小端 u32 ×4（固件魔数） |

**约束**：`[40..56]` 的魔数缺失时命令仍返回成功，但 CAN 引擎不会启动；
StartCAN 必须复用完整的 InitCAN 包，仅把 `[0]` 改为 `0x02`。

波特率映射（Timing0, Timing1）：

| 速率 | Timing0 | Timing1 |
| --- | --- | --- |
| 5 kbit/s | `0xBF` | `0xFF` |
| 10 kbit/s | `0x31` | `0x1C` |
| 20 kbit/s | `0x18` | `0x1C` |
| 50 kbit/s | `0x09` | `0x1C` |
| 100 kbit/s | `0x04` | `0x1C` |
| 125 kbit/s | `0x03` | `0x1C` |
| 250 kbit/s | `0x01` | `0x1C` |
| 500 kbit/s | `0x00` | `0x1C` |
| 800 kbit/s | `0x00` | `0x16` |
| 1000 kbit/s | `0x00` | `0x14` |

## TX 帧

64 字节整包，发送到数据 TX 端点：

| 偏移 | 内容 |
| --- | --- |
| `[0]` | 恒为 `0x01`（远程帧也不能改成 `0x04`） |
| `[1..5]` | ID，小端 u32 |
| `[9]` | `0x01` |
| `[11]` | Remote 标志 |
| `[12]` | Extended 标志 |
| `[13]` | DLC（上限 8） |
| `[14..]` | 数据 |

远程帧把 `[0]` 写成 `0x04` 会导致设备接收计数翻倍（3 帧计 6）。

## RX 传输

每次 bulk IN 读取最多 128 字节，即最多两个 64 字节子块。有效帧可能随机出现在
任一子块中，必须遍历全部子块解码。

每个 64 字节子块：

- 前 8 字节全零 → 空块；
- `block[0]` = 本块帧数（上限 8），从偏移 1 开始；
- 每帧 `13 + raw_dlc` 字节：
  - `[0..4]` ID，小端；
  - `[4..8]` 设备时间戳，小端；
  - `[10]` Remote；
  - `[11]` Extended；
  - `[12]` DLC（原始值，解析时截断到 8，但推进长度用原始值）；
  - `[13..]` 数据。

必须信任 `block[0]` 的帧数，**不能**把 ID 全零当作流结束：ID `0x000` 是合法
CAN 帧（例如 CANopen NMT）。对越界残帧做防御性丢弃，不能 panic——该解码
路径位于 USB 回调/热路径。

## 硬件验收滤波（实测）

固件不直接比较原始 CAN ID，而是使用归一化的 32 位验收值（自测回环实测）：

| 帧类型 | AccCode | AccMask | 说明 |
| --- | --- | --- | --- |
| 标准帧 | `id << 21` | `0x001F_FFFF` | 只比较 11 位 ID，低 21 位不关心 |
| 扩展帧 | `id << 3` | `0x0000_0007` | 只比较 29 位 ID，低 3 位不关心 |
| 接收全部 | `0` | `0xFFFF_FFFF` | Filter=0 或单滤波均可用 |

滤波方式取 1（单滤波）。`AccMask` 中为 1 的位表示不参与比较，因此通过条件可写作
`(frame_filter_value & !acc_mask) == (acc_code & !acc_mask)`，其中
`frame_filter_value` 是固件归一化后的值，而不是裸 ID。

Web UI 的“按 ID 生成”按钮会把用户输入的标准/扩展 ID 转换为上述 AccCode/AccMask；
范围或多 ID 过滤请使用应用层软件过滤器。验证命令：

```bash
cargo test --test hw_filter -- --ignored --nocapture
```

## 打开与关闭

打开：枚举 → `open` → `set_auto_detach_kernel_driver(true)` → `claim_interface(0)`
→ 发送两次 `0x13` 握手并读取 `0x82` → 读取字符串描述符触发工作模式。

关闭：向 `0x02` 和 `0x04` 各发送一次 `0x07` → 等待约 50ms → `release_interface(0)`
→ 释放句柄。关闭后设备约 0.4s（宿主）到数秒（容器 USB 直通）内不可见，
重新打开需要重试窗口。跳过关闭序列会让设备残留异常态。
